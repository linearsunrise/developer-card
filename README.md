# Developer Card

Цифровая визитка разработчика: публичный GraphQL API с профилем,
навыками, опытом работы и проектами.

- [Открыть Apollo Sandbox](https://developer-card-production.up.railway.app/graphql)
- [Проверить готовность сервиса](https://developer-card-production.up.railway.app/health)
- [Исходный код](https://github.com/linearsunrise/developer-card)

Стек: TypeScript, Node.js 22, NestJS 12, Apollo Server 5, GraphQL,
Prisma 7, PostgreSQL 17, Docker. История изменений и миграции хранятся в Git.

## Запуск с нуля

Нужны работающий Docker Engine и Docker Compose. Локальные Node.js и PostgreSQL
для этого сценария не требуются.

```sh
git clone https://github.com/linearsunrise/developer-card.git
cd developer-card
docker compose up --build --wait
```

Откройте <http://localhost:3000/graphql>. Для загрузки интерфейса Sandbox браузеру
нужен интернет. Проверка готовности: <http://localhost:3000/health>.

Compose запускает PostgreSQL и ждёт его готовности. Контейнер приложения затем
применяет SQL-миграции, выполняет seed и запускает NestJS. Ошибка миграции или seed
останавливает запуск. Файл `.env` для Compose не нужен.

Порты хоста: `3000` для API и `5431` для PostgreSQL. Внутри Docker приложение
подключается к `db:5432`. Учётные данные из Compose предназначены для локального запуска.

```sh
docker compose logs -f api
docker compose down
```

Данные сохраняются в Docker volume. Команда `docker compose down -v` удаляет
локальную базу; следующий запуск создаст её заново из миграций и seed.

## Пример запроса

```graphql
query BusinessCard {
  profile {
    name
    description
    links {
      label
      url
    }
    skills {
      name
    }
    experience {
      company
      position
      startDate
      endDate
      achievements
    }
    projects {
      name
      url
    }
  }
}
```

Можно запросить только нужные поля: `{ profile { name } }`.
Если профиль отсутствует, API возвращает `profile: null`; отсутствующие коллекции - `[]`.
`endDate: null` означает текущую работу. Периоды работы в резюме имеют точность до
месяца: первое число обозначает месяц, а не фактический день трудоустройства.
В БД используются `DATE`, в API ISO-даты с временем в полночь UTC.

## Архитектура и решения

```text
src/
  profile/     GraphQL-модели, resolver, service, repository, DataLoader
  database/    Prisma client и lifecycle подключения
  app.module.ts
  health.controller.ts
  main.ts
prisma/
  schema.prisma
  migrations/  Версионируемые SQL-миграции
  profile.data.ts
  seed-profile.ts
  seed.ts
test/          HTTP-тесты, тесты загрузчиков и интеграция с PostgreSQL
```

- **Resolver** описывает GraphQL API и разрешение вложенных полей. Code-first
  схема строится из отдельных TypeScript-моделей; служебные поля БД не раскрываются.
- **Service** выбирает единственный публичный профиль `main`. Бизнес-правил мало,
  поэтому сервис небольшой.
- **Repository** содержит Prisma-запросы и сортировки. Загрузчики коллекций
  обращаются к нему напрямую: дополнительных бизнес-правил для коллекций нет.
- **DatabaseModule** предоставляет один Prisma client через Nest DI, подключает
  его при старте и закрывает соединения при остановке.

Один предметный модуль соответствует масштабу задачи. Универсальный CRUD,
административная панель и авторизация не нужны для публичной визитки только для чтения.

PostgreSQL обеспечивает внешние ключи, транзакции и одинаковую модель данных
локально и на хостинге. Профиль связан с таблицами ссылок, навыков, опыта и проектов.
Достижения хранятся массивом строк: собственного жизненного цикла у них нет.
Навыки принадлежат профилю; общий справочник для одного владельца избыточен.
Коллекции сортируются по `sortOrder`, опыт по убыванию `startDate`, с ID как
дополнительным критерием. Индексы поддерживают выборку по профилю и сортировку.

### Вложенные поля и SQL

Связи загружаются лениво через field resolvers. DataLoader создаётся для каждого
HTTP-запроса, объединяет ключи родителей через `IN` и кэширует повторные обращения
в пределах этого запроса. Результаты возвращаются в порядке ключей, включая пустые
списки. Между запросами кэш не сохраняется.

Интеграционные тесты считают реальные SQL-запросы через события Prisma:

| Сценарий                                    | SELECT-запросов |
| ------------------------------------------- | --------------: |
| Только имя                                  |               1 |
| Профиль и все четыре коллекции              |               5 |
| Навыки через два алиаса                     |               2 |
| Два корневых алиаса профиля с навыками      |               2 |
| Полная визитка после добавления 100 навыков |               5 |

В проверенном сценарии Prisma также объединяет одинаковые корневые `findUnique`.
Это поведение закреплено тестом для используемых версий зависимостей.
Проверяется и пакетная загрузка навыков для нескольких разных родителей.

Для единственного профиля четыре запроса связей сами по себе не являются N+1:
их количество не зависит от числа элементов коллекции. DataLoader дополнительно
устраняет повторное чтение связей через алиасы и поддерживает несколько родителей.
Преобразование GraphQL AST в Prisma `select` не используется: незапрошенные связи
не читаются, но скалярные столбцы выбранной таблицы загружаются целиком.

### Миграции и заполнение базы

Источник данных `prisma/profile.data.ts`. Для изменения визитки отредактируйте
его и пересоберите приложение. `migrate deploy` применяет сохранённые миграции;
`db push` при запуске не используется.

Seed выполняется в одной транзакции: обновляет профиль `main`, заменяет его
коллекции и удаляет устаревшие записи. Повторный запуск не создаёт дубликаты.
Ручные изменения этого профиля в БД перезаписываются данными из файла.
Другие профили не обновляются. Advisory lock сериализует параллельные seed-запуски.

### Ошибки и остановка

`GET /health` проверяет доступность БД: `200` при успехе, `503` при ошибке.
GraphQL скрывает детали внутренних ошибок, сохраняя диагностические серверные логи;
ошибки валидации запросов остаются информативными. GraphQL-ошибка может прийти с HTTP
`200`, поэтому клиент должен проверять поле `errors`.

Docker запускает сервер непривилегированным пользователем `node`. Entrypoint
использует `exec`, а Nest shutdown hooks закрывают Prisma при остановке.
Сборка многоэтапная, зависимости фиксирует lock-файл. Prisma CLI оставлен в runtime,
поскольку миграции применяются при старте.

## Локальная разработка

Нужен Node.js 22, (лучше 22.12+). PostgreSQL можно запустить через Compose:

```sh
docker compose up -d db
cp .env.example .env
npm ci
npm run build
npm run start:ready
```

Если API-контейнер уже работает, предварительно выполните `docker compose stop api`,
чтобы освободить порт 3000. `start:ready` выполняет миграции, seed и запуск;
`npm start` запускает только уже собранный сервер.

Для разработки после начальной подготовки запустите `npm run build:watch`
и `npm run start:dev` в двух терминалах.
После изменения схемы выполните `npx prisma migrate dev --name short_description`,
затем `npm run build`. Новый SQL-файл необходимо сохранить в Git.

## Тесты и CI

```sh
npm ci
npm run check
```

Команда проверяет форматирование, сборку и семь тестов HTTP API и загрузчиков.
Для шести интеграционных тестов нужна отдельная одноразовая база с именем,
оканчивающимся на `_test`. Тесты изменяют её данные.

Создайте тестовую базу один раз:

```sh
docker compose up -d db
docker compose exec db createdb -U card card_test
```

Задайте переменные в текущем терминале. Bash:

```sh
export DATABASE_URL='postgresql://card:card@localhost:5431/card_test?schema=public'
export TEST_DATABASE_URL="$DATABASE_URL"
```

PowerShell:

```powershell
$env:DATABASE_URL='postgresql://card:card@localhost:5431/card_test?schema=public'
$env:TEST_DATABASE_URL=$env:DATABASE_URL
```

Затем выполните:

```sh
npm run db:migrate
npm run test:integration
```

Для обычного запуска вернитесь в новый терминал, чтобы не использовать тестовый
`DATABASE_URL`. Тесты проверяют фактические SQL-запросы, кэширование, порядок данных,
отсутствующий профиль и повторный seed с удалением устаревших записей.

GitHub Actions запускает проверки с PostgreSQL, затем отдельно собирает Docker
и ожидает готовности Compose с новой базой. Вручную также проверены запуск чистого
клона, восстановление после отказа БД, повторный запуск, остановка по SIGTERM и
отказ запуска без `DATABASE_URL`. Эти проверки отказов не входят в CI.

## Развёртывание

Приложение размещено на Railway. Сервис API собирается из корневого Dockerfile,
PostgreSQL работает отдельным сервисом. Настройки приложения:

| Настройка             | Значение                                                       |
| --------------------- | -------------------------------------------------------------- |
| `DATABASE_URL`        | Внутренняя строка подключения PostgreSQL, заданная на хостинге |
| `PORT`                | `3000` или порт, предоставленный платформой                    |
| Healthcheck path      | `/health`                                                      |
| Публичная точка входа | `/graphql`                                                     |

Используется команда запуска из Dockerfile, без замены на `npm start`, чтобы
сохранить автоматические миграции и seed. База должна быть готова перед запуском
API. Пароли и production `.env` в репозиторий не добавляются.

Sandbox и introspection включены намеренно, в том числе в production: это часть
задания. При переходе к нескольким репликам миграции и seed стоит вынести в
отдельный release job. Ограничение частоты и стоимости GraphQL-запросов пока
не реализовано; для более широкого публичного использования его следует добавить.
